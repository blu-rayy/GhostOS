## 4. Defects and decisions

| ID | Severity | Owner | Finding |
|---|---|---|---|
| **DA-1** | **Medium** | Dev 1 | **Contradictory category corrections are accepted.** `PATCH` only checks `merchant/date/amount/currency` against the profile, so `{category:"receipt"|"invoice", accept:true}` is accepted for `identity_or_civil`, `statement`, `legal` and `medical`. Effect: misfiling. A dated statement is planned into `GhostOS Organized/Invoices/2026-09/`. The totals gate still holds, so it is not counted. The contract requires the backend to "reject contradictory combinations". |
| **DA-2** | Medium | Dev 2 | The ambiguous cash-payment note (GT `uncertain`) is classified `receipt` / `transaction`, so the user gets the Shop/Date/Amount form instead of the uncertain flow. No values were invented (all null, review required). |
| **DA-3** | Low | Dev 1 / Dev 2 | Transaction fields are kept on non-transactional records: the card statement and utility bill keep `date` and `currency` (only `amount` is nulled). Not displayed by the UI and not counted, but stored and returned by the API. Suggest stripping them, or keeping them only as evidence. |
| **DA-4** | Decision | Dev 1 + Dev 4 | **Utility bills:** the ground truth treats `meralite-power-bill` as a payable invoice (PHP 3,412.75), while the contract lists "utility … statement" as non-expense. The model now says `statement`, which removes it from totals. Decide which applies. QA will then update the ground truth (Dev 4) or Dev 2 will adjust the prompt. Expected outcomes were **not** changed to fit the result. |
| **DA-5** | Low / decision | Dev 1 | When `document_kind` is null, the legacy fallback derives `transaction` from `category`. A statement labelled `invoice` with a null kind would become countable. Not observed in this run; consider `uncertain` for new records with a null kind. |
| Obs. | Info | Dev 2 | `notes/project-tracker.csv` → kind `uncertain` (an extra review, safe). The injection note → `uncertain` (safe). |
| Gap | Info | Dev 4 | The original 20 fixtures have no `expected_document_kind` / `expected_field_profile`. QA used labelled, contract-derived expectations for them. |

Still separate and open: **D1** (cross-scan document IDs). Not exercised; one fresh scan was used. **F1** was fixed earlier ([F1 retest](../phase3_acceptance/f1_retest/f1_retest_report.md)).
